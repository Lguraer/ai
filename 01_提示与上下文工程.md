## 一、这类知识解决什么问题

提示工程（prompt engineering）讨论的是「怎么问」，上下文工程（context engineering）讨论的是「给模型看什么」。后者是前者在生产环境中的升级版：当你的系统需要拼接文档、历史对话、工具返回、用户画像时，问题不再是句子怎么写，而是**token 预算怎么分配**。

这个领域正在经历一次重心转移。早期讨论集中在提示词的措辞技巧（角色扮演、思维链、few-shot），现在的主流讨论集中在上下文的结构：哪些信息进、哪些不进、以什么顺序进、超预算时先砍谁。

一个关键认知：**上下文不是越多越好**。无关内容会稀释注意力，长上下文还会显著推高延迟与成本。多份实测指出，往 Agent 里塞向量库有时反而降低准确率。

## 二、核心知识骨架

**提示的四要素**　角色（谁在说）、任务（要做什么）、约束（不能做什么）、输出格式（怎么交付）。缺任何一项都会让模型自行补全，而模型的补全通常不是你想要的。

**上下文预算**　一次请求的 token 是有限资源，要在「系统指令 / 检索文档 / 对话历史 / 工具返回 / 输出预留」之间分配。工程上的做法是给每类设上限，超限时按优先级截断，而不是让某一类无限膨胀。

**结构化输出**　让模型输出 JSON 而不是自然语言，是让 LLM 进入软件系统的前提。要点：给 schema、给示例、失败重试、校验兜底。多数框架已支持约束解码（constrained decoding），但仍需在应用层校验。

**推理模型的行为差异**　推理模型（reasoning models）会先产生隐藏的思考 token 再回答，这些 token 计入成本与延迟。任务简单时用推理模型是浪费；任务需要多步推导时，普通模型即使给思维链提示也追不上。

**失效模式**　四类高频问题：指令冲突（系统提示与用户输入矛盾）、上下文污染（错误信息被反复引用）、格式漂移（多轮后输出结构崩坏）、过度约束（限制太多导致模型放弃执行）。

## 三、常见误区

- **把提示词当咒语**。加「请一步步思考」「你是一个专家」这类话，在新一代模型上收益已经很小，真正有效的是把任务拆清楚、把判断标准写明。
- **忽视上下文长度成本**。塞满 100K token 的检索结果，成本是 10K 的十倍，而准确率可能更低。
- **只测成功案例**。提示词的真实质量由边界情况决定：空输入、超长输入、多语言混合、恶意输入。
