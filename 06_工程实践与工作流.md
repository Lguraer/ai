## 一、这类知识解决什么问题

AI 编程助手（Claude Code、Cursor、Copilot 等）已经把「生成代码」变成了廉价动作，瓶颈转移到了**审阅与验证**。这会带来一个结构性变化：写代码的时间下降，读代码的时间上升。

同时出现了一类新的工程实践：用 Agent 跑长任务（重构、迁移、批量修改），需要配套的东西不是提示词，而是**约束**——测试、类型检查、lint、CI。这些是 Agent 的「验收器」，没有它们，Agent 的产出无法判断对错。

另一条主线是本地化：Ollama、llama.cpp 让模型跑在本机，适合隐私敏感与离线场景，代价是能力弱于云端前沿模型。

## 二、核心知识骨架

**三种使用模式**　① 补全式（写的时候提示下一行）② 对话式（描述需求，生成整段）③ Agent 式（给目标，自主多步执行）。三者的风险递增：补全错一行，Agent 可能改错十个文件。

**验收基础设施**　Agent 产出的可信度取决于验证手段：单元测试覆盖、类型系统、lint 规则、CI 门禁。没有这套东西，Agent 越快越危险。

**代码审阅的转向**　人的角色从「写」变成「审」。审阅要点：改动范围是否超出预期、是否引入隐式依赖、错误处理是否被删掉、测试是否同步更新。

**本地模型栈**　Ollama / llama.cpp / vLLM 提供本地推理。适合：数据不能出内网、需要离线、高频低价值任务降本。不适合：需要前沿推理能力的复杂任务。

**多 Agent 并行**　已有实践用多个 Agent 并行处理不同模块，人的工作是分配任务与合并结果。前提是模块边界清晰、接口稳定。

## 三、常见误区

- **不看 diff 就合并**。Agent 会「顺手」改动无关代码，也会删掉它认为多余的防御性检查。
- **在没有测试的项目上用 Agent**。没有验收器，等于把风险直接推到生产。
- **用 Agent 做架构决策**。它可以实现方案，但不擅长判断该不该这么做。
- **忽视成本**。Agent 长任务的 token 消耗可能是手工的几十倍。

## 五、推荐学习顺序

1. 先补齐验收基础设施：测试、类型、lint、CI
2. 从补全式开始用，建立对工具边界的直觉
3. 过渡到对话式，每次只让它改一个明确的函数/文件
4. 再尝试 Agent 式长任务，但要求它每步产出可验证的中间结果
5. 建立 diff 审阅清单，把「必须人工确认」的项固定下来
